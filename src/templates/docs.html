Documentation

Melodie A11Y

Melodie measures the accessibility of Android Jetpack Compose screens generated by LLMs, fixes the violations with an LLM, and measures again.

Every run follows the same path: generate the code, compile it into a real APK, check it with static rules (Lint and a Compose scanner) and with Google's Accessibility Test Framework (ATF) on a physical device, and save a JSON report.

Quick start

  1. Install Docker. Docker Desktop on Windows or macOS, or Docker Engine with Compose on Linux.
  2. Create the settings file. In the project folder, copy .env.example to .env. API keys are optional there: you can also type them on the pages.
  3. Start Melodie. Run docker compose up --build. The first run downloads the Android SDK and takes a few minutes.
  4. Open the interface at http://localhost:8000.
  5. Connect a phone (optional). Without one, the static checks still run and ATF is skipped with a warning. See Android device.

Analysis

Generates the screen you describe with the selected LLMs and runs the full pipeline on each answer.

  1. Select the LLMs. Click an LLM in the list to select it. Its fields open: paste the API key and, if you want, change the model. Blank fields use the .env key and the default model. Ollama runs locally and needs no key.
  2. Write the prompt. Describe the screen, or pick a preset prompt. Use Few-shot to add examples the LLM should follow.
  3. Set the options in the output header: number of runs (1, 3, 5 or 10) and Retry, which sends compilation errors back to the same LLM up to 2 times.
  4. Click Run Pipeline. The terminal shows each stage. When it ends, the report opens next to it.

Keys typed on the page go only to that run and stay in the browser tab until it is closed. They are never written to disk.

Correction

Sends the code of a report and its list of violations to a correction model, which returns the corrected code. The correction prompt asks the model to fix only the listed violations.

  1. Select a report in the sidebar. Its violations are listed below it.
  2. Choose the correction model. Pick one option and fill in its fields. Blank fields use the .env values and the default model.
  3. Click Fix violations via API. The corrected file is saved in outputs/codes/ and the Re-analysis tab opens with it selected.
OptionNeeds
Lab server (Open WebUI)Server URL and Open WebUI token. The server may only be reachable over the lab's VPN.
OllamaOllama running on your machine. No key.
Other server (OpenAI-compatible)Server URL and model name; key only if the server asks for one. Works with LM Studio, vLLM and llama.cpp.
OpenAI, Anthropic, Gemini, Groq, DeepSeek, xAIYour API key.

Re-analysis

Compiles and analyzes a corrected file with the same checks, so the result can be compared with the original report.

  1. Open the Re-analysis tab on the Correction page.
  2. Select the corrected file. Use the pencil button to rename it; the link to its source report is kept.
  3. Click Start re-analysis. The report shows the violations left and the trend across re-analyses.

Reports

Lists every saved analysis. Filter by prompt or LLM, open a report to see its violations, timings and generated code, and download it as JSON. Each report contains:

  • the prompt, LLM, date and analyzer version;
  • the build status and the time of each stage;
  • the Lint, static and ATF violations, with the line or screen position of each one;
  • the generated code.

CHASE 2027 battery

The battery measures how well an LLM repairs the accessibility of screens generated by other LLMs. It is run on the CHASE 2027 page.

The page has three columns: the form to analyze a test, the pipeline output, and the battery grid. Each grid cell is one screen and one AI, with three dots: analyzed, corrected and re-analyzed.

Before you start: calibration

Run the three calibration screens before the battery. Each has a known expected result, so they show whether the analyzer is counting correctly on your device.

  1. Pick a calibration screen in Calibration and validation screens. The code is filled in for you.
  2. Click Build and analyze and compare the result with the expected values.
ScreenMeasuresExpected
CalibracaoLimpaScreenFalse positivesLint 0 · Static 0 · ATF 0
CalibracaoDefeitosScreenEach planted defect is found, and only itLint 2 · Static 4 · ATF 3 (ST 2 · CT 1)

If a calibration screen does not match, stop and find the cause before running the battery.

Generation rules

The same rules apply to the three models:

  1. One new conversation per screen, with no history.
  2. Memory and custom instructions off, or an account without personalization.
  3. Paste the whole prompt from prompts/bateria_chase2027/, without editing it.
  4. Use the first answer. Do not regenerate or ask for changes.
  5. Exception, build failure: if the code does not compile because of the AI, paste Melodie's repair prompt in the same chat, up to 2 times. After 2 repairs, the screen is recorded as a build failure.

Running a test

  1. Choose the test. Click its cell in the grid, or pick the screen and the AI in the form. The test name is filled in, for example 01_login_claude.
  2. Generate the code. Click Copy prompt, paste it in a new chat with that AI and copy the first answer.
  3. Analyze. Paste the answer in Kotlin code (the whole ```kotlin block works) and click Build and analyze.
  4. If it does not compile, click Copy repair prompt, paste it in the same chat and analyze the new answer. Melodie counts the repair attempts.
  5. Fix. Click Fix this report. The Correction page opens with the report selected; choose the correction model and run it.
  6. Re-analyze. The Re-analysis tab opens with the corrected file selected. Click Start re-analysis.
  7. Next. Back on the CHASE 2027 page, click Next test to jump to the next cell that has not been analyzed.

Batch and redo

  • Fix all corrects, one at a time, every analyzed screen that has violations and has not been corrected (about 1 minute per screen). It uses the default correction model from .env.
  • Re-analyze all re-analyzes every corrected file that has no re-analysis (about 4.5 minutes per screen; keep the phone on).
  • Stop halts the batch after the current screen.
  • Selecting a cell shows its files and the buttons Redo correction, Redo re-analysis and Delete to redo.
  • Restart battery clears every test except the calibration screens.

Deleted files are moved to outputs/lixeira and can be recovered.

Export CSV builds one row per test with the counts before and after, the reduction in percent, the categories that got worse, the analyzer versions, the ATF read status and the repair attempts. The column names are in Portuguese, as used in the results spreadsheet.

When a result is valid

Below each result, the page shows whether ATF actually read the screen. Redo the analysis when it says so.

  • ATF read: the first pass must see the app's nodes (pass 1: N nodes with N > 1). Without this, a result of 0 proves nothing.
  • Light mode: Melodie switches the phone to light mode before ATF. A run recorded in another mode is not valid.
  • Phone awake: keep it unlocked with the screen on during the analysis.
  • Build failures: before blaming the AI, check whether a "fixed …" message from Melodie's pre-processor is related to the error.

Pipeline stages

1 GenerationThe prompt goes to the LLM.
2 ExtractionKotlin blocks are extracted and 55 rules fix known build errors.
3 BuildGradle builds a real APK.
4 StaticLint rules and the Compose scanner.
5 ATFGoogle's ATF on the device, scrolling the screen.

Build environment: compileSdk/targetSdk 36, Kotlin 1.9.22, AGP 8.2.2, Compose BOM 2024.02.00, ATF 4.1.1.

Every contentDescription = null counts as a violation, including decorative icons. The analyzer does not decide whether an icon is decorative.

Configuration

Settings live in .env. Everything is optional: keys and servers can also be typed on the pages.

# LLM keys
GEMINI_API_KEY=
GROQ_API_KEY=
OPENAI_API_KEY=
ANTHROPIC_API_KEY=
DEEPSEEK_API_KEY=
XAI_API_KEY=

# Local Ollama
OLLAMA_MODEL=llama3.2

# Android device for ATF
EMULATOR_HOST=host.docker.internal
ADB_KEYS_DIR=C:/Users/<your_user>/.android

# Default correction model
CORRECTOR_PROVIDER=labserver
LAB_SERVER_BASE_URL=
LAB_SERVER_TOKEN=
LAB_SERVER_MODEL=qwen3-coder-30b-a3b-instruct-fp8

After changing .env, restart with docker compose up.

Android device

  1. Enable Developer options. On the phone, open Settings → About phone and tap Build number 7 times.
  2. Enable Wireless debugging in Developer options and pair the phone with your computer.
  3. Connect from your computer: adb connect <phone_ip>:5555.
  4. Check with adb devices: the phone must appear as device.
  5. Point Docker to your ADB keys with ADB_KEYS_DIR in .env, so the container is trusted by the phone.
