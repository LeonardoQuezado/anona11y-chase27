## 0. Headline numbers (to quote)

- **30 screens** generated: 10 screen types × 3 LLMs (Claude, ChatGPT, Gemini), from **accessibility-neutral prompts**.
- **27/30 compiled on the first attempt.** The other 3 compiled after one compiler-guided repair (Claude 10/10, ChatGPT 9/10, Gemini 8/10).
- **27/30 screens had at least one accessibility defect**: **82 defects** in total (unique code defects + runtime results; median 2 per screen, maximum 12).
- The most frequent defect: a **heading without heading semantics** (25 occurrences in 24 screens).
- **Runtime checks (Google ATF) found almost nothing**: 0 missing speakable text, 3 small touch targets, 8 low-contrast texts (all 8 in two Profile screens). Most defects are **semantic and only visible in the code**.
- **Repair** (Qwen3-Coder-30B, one pass, frozen prompt v5) on the 27 screens with defects:
  - 26 repaired screens still compiled (1 broke the build);
  - in those 26, defects fell from **75 to 20 (−73%)**;
  - **16/26 screens left with no detected defect**.
- **Sensitivity:** excluding decorative icons with `contentDescription = null` (counted as defects by policy), the reduction is **61%** (51 → 20). Excluding the Music Player screen (on which the repair prompt was developed), it is 74%.
- **Side effects of repair**: **6/26 screens gained a new defect** (5 vague content descriptions, 1 new contrast failure), and **1/27 repaired screens no longer compiled**.

## 1. Context

- **Tool:** Melodie A11Y. A FastAPI + web interface that compiles LLM-generated Jetpack Compose screens, analyses their accessibility statically (Android Lint with custom UAST rules + a Compose static scanner) and at runtime (Google ATF on a physical device), sends the violations to an LLM repairer, and re-analyses the repaired code. Every analysis, repair and re-analysis is traceable through a shared label (e.g. `04_user_profile_chatgpt`).
- **Repository:** `leonardoquezado/accessibility-llm-pipeline`, branch `claude/upbeat-hamilton-UJYWu`.
- **Authors:** Leonardo Quezado de Meneses (lead), Windson Viana, François **[FILL IN surname]** (HEC Montréal / Tech3Lab). **[FILL IN affiliations]**
- **Venue:** CHASE 2027, extended abstract.
- **Prior work:** WebMedia 2026 (best-paper nominee), an earlier version of the pipeline. **Do not reuse or compare its numbers.** They were measured with analyser v1, whose ST and text-field-label counts had false positives and which skipped the top of scrolling screens (see §4.4). Cite WebMedia as prior work only.

### Suggested research questions
- **RQ1 — Prevalence:** how accessible are Jetpack Compose screens generated by general-purpose LLMs from prompts that do not mention accessibility?
- **RQ2 — Detection:** which defects are detected statically (code) and which at runtime (ATF), and where are the blind spots?
- **RQ3 — Repair:** how much does a one-pass LLM repair reduce the detected defects, and what does it break or introduce?

## 2. Method

### 2.1 Screens and prompts
Ten screen types, one prompt each (`prompts/bateria_chase2027/*.txt`). Each prompt has a functional description plus a fixed technical suffix (compilation constraints).

| # | Screen | Functional description (abridged) |
|---|---|---|
| 01 | Login | welcome message, email and password fields, Login button, "Forgot Password?" text button |
| 02 | Registration | first/last name, email, password, date of birth, gender dropdown, Submit/Cancel |
| 03 | Product details | image placeholder, name, description, price, Add to Cart / Favorite |
| 04 | User profile | circular photo placeholder, 4 fields, Edit/Save toggling view and edit mode |
| 05 | Music player | track and artist, progress with times, play/pause/skip icon buttons, scrollable playlist |
| 06 | Navigation drawer | retractable drawer with 2 item groups and a divider, top app bar toggle |
| 07 | Video player | video placeholder, playback controls, slider with times, fullscreen and volume icon buttons |
| 08 | Post feed | scrollable posts with avatar, author, time, text, optional image, Like/Comment/Repost icon buttons with counts |
| 09 | Banking home | top bar with profile/search icon buttons, balance card with show/hide, 6 shortcut icon buttons, transactions list |
| 10 | Notifications | scrollable list with leading icon, title, description, time; unread state toggled by tap |

**Accessibility-neutral prompts ("level 1"):** compared with the pipeline's original suffix, three cues that could prime the model were removed:
- "evaluated by an accessibility pipeline" became "evaluated by a pipeline";
- "and always provide contentDescription" was removed from the icon rule;
- the package name line was removed.

The technical constraints are unchanged: Material 3 only, no external libraries, `Icons.Filled.*`, a single Kotlin file, no custom theme or color scheme, hard-coded English strings.

### 2.2 Generation protocol
- **Models:** Claude, ChatGPT and Gemini, through their public chat interfaces (no API). **[FILL IN the model name/version shown in each interface and the date]**. Generation took place on 27 Oct 2026.
- **Session:** one new chat per screen, with no memory or custom instructions.
- **Input:** the whole prompt file, pasted unchanged.
- **First answer:** the first answer is used; no regeneration or content follow-up.
- **Compile-failure exception (decided before the failures were analysed):** if the code does not compile because of the model's own error, the same repair prompt as the pipeline's automatic SELF_REPAIR (`src/repair_prompt.py`) is pasted into the same chat, up to 2 times. The prompt contains the compiler errors and the failed code, with the instruction to fix only those errors.
  - Used 3 times, 1 attempt each: `01_login_gemini`, `07_video_player_gemini`, `08_post_feed_chatgpt`.
  - Example (Gemini login): `MaterialTheme.colorScheme.headlineLarge`, i.e. a typography token read from the color scheme.

### 2.3 Build and device
- **Pre-processing:** a deterministic pre-processor normalises frequent API slips (package, `onCreate` signature, missing imports, Material 2 names, etc.). Every applied fix is logged.
- **Pre-processor audit (v2):** it was audited after it renamed a model's own `val backgroundColor` and broke valid code. Renames now apply only to named arguments, never to names the code declares; text fixes skip string literals; 11 regression tests check that valid code is untouched.
- **Theme injection:** the pre-processor makes `MaterialTheme` follow the system theme, and **the device is forced into light mode** before every runtime run (`cmd uimode night no`; the mode is stored in each report). Rationale: on a phone in dark mode, the injected dark scheme combined with model-chosen light backgrounds produced contrast failures that were not in the model's code.
- **Toolchain:** AGP 8.2.2, Kotlin 1.9.22, Compose compiler 1.5.8, Compose BOM 2024.02.00, compileSdk/targetSdk 36, minSdk 24.
- **Device:** Motorola edge 60 fusion, Android 16, physical, connected over ADB/Wi-Fi. Screen kept awake, light mode.

### 2.4 Analysers (version v2.8; one re-analysis on v2.9)
**Static (code):**
- **Android Lint + custom UAST rules:**
  - Icon/Image with missing or null `contentDescription`;
  - TextField/OutlinedTextField without `label`;
  - arguments are mapped through the resolved call, so both named and positional arguments are handled.
- **Compose static scanner:**
  - the same description and label checks;
  - IconButton whose only icon has a null description;
  - `ComposeSmallTouchTarget`: clickable or interactive component declared below 48 dp, following the modifier order (the outermost fixed size wins; padding between it and the clickable shrinks the area);
  - `ComposeMissingHeading`: `Text` with a display/headline style and no `semantics { heading() }`;
  - `ComposeVagueContentDescription`: empty, jargon ("placeholder") or naming the element type ("icon", "button", "image"…);
  - `ComposeFocusLossOnToggle`: an if/else whose button flips the condition and removes itself, with no FocusRequester or liveRegion;
  - `ComposeDisabledFieldWithValue`: field disabled by a state to show data. **Beyond WCAG** (disabled controls are exempt from 1.4.3); reported apart and not counted.

**Runtime (device):**
- **Engine:** Google Accessibility Test Framework 4.1.1, run on the `AccessibilityNodeInfo` tree (Espresso's integration cannot see Compose content).
- **Checks:**
  - **ST** `SpeakableTextPresentCheck`: ATF counts non-focusable children's text, as TalkBack does;
  - **TT** `TouchTargetSizeCheck`: 48 dp;
  - **CT** `TextContrastCheck`.
- **What counts:** ATF ERROR results, plus the screenshot-estimated contrast below the required ratio. ATF labels that contrast result a WARNING because Compose text colours can only be estimated. The "borderline" warning is not counted.
- **Scrolling:** the test waits for Compose's accessibility tree, scrolls in slow overlapping steps until the content stops moving, skips elements cut by the scroll edge, and de-duplicates results by position in the content.
- **Validity:** every run stores per-pass diagnostics and the device theme. A run counts only if its first pass read the app's nodes and the theme was light. All 30 analyses and all 26 compiled re-analyses met this rule.

### 2.5 Counting
- **Unique code defects:** Lint and the static scanner overlap. The same defect at the same line counts once, and an IconButton flagged together with its null icon counts once. The total raw count is reported only for reference.
- **Primary measure:** unique code defects + ATF results (ATF counts rendered elements: an icon button inside `repeat(3)` is 1 in code and 3 at runtime).
- **Decorative-icon policy:** every Icon/Image with `contentDescription = null` counts as a defect, even when decorative (next to text, or in a labelled field's slot). This is stricter than Android guidance, so results are also reported without the decorative ones (`null_decorative`, detected automatically).

### 2.6 Repair and re-analysis
- **Repairer:** `qwen3-coder-30b-a3b-instruct-fp8`, served by the Tech3Lab (HEC Montréal) endpoint, temperature 0.1.
- **Calls:** one call per screen; retries happen only for network errors. Each call is independent, with no history between screens.
- **Input:** the pre-processed code plus the list of detected violations (source, line, message).
- **Prompt v5, frozen:** it was developed iteratively (v1–v5) on the ChatGPT Music Player screen in Sept–Oct 2026, before this battery (`results/CORRECTION_LOG.md`). It does not cover the categories added in analyser v2.6 (heading, vague description, focus loss, disabled field); the model only receives their messages, which include a fix hint.
- **Re-analysis:** the repaired file is re-analysed with the same pipeline. A repaired file that does not compile is a failed repair.
- **Screens corrected:** all 27 screens with at least one defect. The 3 defect-free screens were not sent.

**Notes:**
- "Other code defects" are null/missing descriptions, unlabelled fields and unlabelled icon buttons (counted once per code location).
- The 8 CT results are all in two Profile screens (Claude, Gemini): low-contrast text of disabled fields used to display data.
- Claude produced **no decorative null icons**; ChatGPT and Gemini produced 12 each. This alone explains a large part of the between-model difference.

### 4.2 Detection: static vs runtime (RQ2)
- **Runtime (ATF) results over the 30 screens:** ST 0, TT 3, CT 8.
- **Static defects:** 25 headings without semantics, 9 vague descriptions, 3 focus losses on toggled content, 3 small declared touch targets, 31 null/missing descriptions or unlabelled fields (24 of them decorative null icons/images).
- **Conclusion:** the generated screens pass the classic runtime checks almost entirely, while their **semantic** accessibility (structure, meaningful names, state changes) fails. Runtime testing alone would report these screens as nearly accessible.
- **Known blind spots (documented with planted cases in the coverage screen, never detected):**
  - redundant descriptions (an icon described as "Save" next to the text "Save" is read twice);
  - state not announced (toggle that only changes colour);
  - gesture-only targets invisible to TalkBack (`pointerInput`);
  - input purpose (WCAG 1.3.5; no API in this Compose version);
  - focus loss outside the if/else pattern.
- **Manual review example:** the User Profile from Claude scored 0 on analyser v2.5. It used disabled fields to show the data (≈2.4:1 contrast, announced as "disabled"), swapped the Edit button away without moving focus or announcing the change, had a title without heading semantics and a jargon description ("Profile photo placeholder"). This led to the four v2.6 rules (§4.4).

**By category, before (30 screens) → after (26 repaired, compiled):**
- headings 25 → 2;
- vague descriptions 9 → 6 (every original one was fixed; all 6 remaining were **introduced** by the repair);
- focus loss 3 → 2;
- static TT 3 → 0;
- ATF TT 3 → 2;
- CT 8 → 8 (4 introduced, 4 not repaired);
- ST 0 → 0.

**Side effects:**
- **New vague descriptions in 5 screens** (Product–ChatGPT, Music–Gemini, Post Feed–ChatGPT, Banking–Gemini, Notifications–Gemini). Likely cause: prompt v5 contains the example `contentDescription = "Play button"`, i.e. the frozen repair prompt teaches the pattern the v2.6 rule flags.
- **New contrast failures, Profile–ChatGPT 0 → 4.** The repairer fixed "TextField without label" by adding a `label` inside fields that stayed **disabled**: it ignored the suggested `readOnly`. The new labels inherit the disabled colour (2.33:1). A defect ATF could not see (disabled value text) became one it can see.
- **Redundant descriptions created by the policy.** In the same screen, the repairer gave descriptions to decorative icons next to text ("Save" + "Save", "Edit profile" + "Edit Profile"). TalkBack reads them twice. Melodie does not detect this (blind spot), so the strict null policy improves the numbers while possibly worsening the experience.
- **Build broken, Profile–Claude.** The repair was otherwise good (`readOnly`, heading, better description). It wrote `.semantics { liveRegion = "Editing mode activated" }`, a type error: `liveRegion` takes a `LiveRegionMode`. Melodie's own focus-loss message suggests "announce it with `Modifier.semantics { liveRegion = … }`", which probably induced the error. Even if it compiled, a live region on the button that disappears would not solve the focus loss.

The instrument was validated and corrected **before and during** the battery. Every report stores `meta.analyzer`; the CSV has `analisador_antes/depois`.

| Version | Problem found | Fix |
|---|---|---|

| v2.3 | Coverage screen: first ATF pass empty (Compose exposes its tree only after an accessibility client connects), so the top of scrolling screens went unchecked; clipped elements at scroll edges gave false ST/TT | connect first, wait for a stable tree, slow overlapping scroll, skip clipped elements |
| v2.4 | Overlapping passes counted elements twice | de-duplication by content position |
| v2.5 | A result of 0 carried no proof the screen was read | diagnostics always returned; validity rule |
| v2.6 | Manual review of a 0-defect screen (§4.2) | heading, vague description, focus loss, disabled field (beyond WCAG) |
| v2.7 | Pre-processor broke valid code (renamed the model's own `backgroundColor`) | safe renames; audit of all fixers; 11 tests |
| v2.8 | Dark-mode device created contrast failures not in the model's code | light mode forced and recorded |
| v2.9 | One re-analysis counted 4 labels twice: a stale node snapshot missed a scroll | scroll measured on the same hierarchy ATF checks; the affected re-analysis (Profile–ChatGPT) re-run: CT 4 |

A **phone that was locked/dark** left the app STOPPED and the test never read the screen; this produced a "0" in one early run. Since v2.5 such runs are flagged and were redone. The pipeline now wakes the device and shows the app over the lock screen.

## 5. Threats to validity and limitations
- **Single screens:** no navigation, dialogs or real data; static content. External validity to full apps is limited.
- **Sample:** 10 screen types × 3 models, one generation each (no repetition). Chat interfaces change over time, so record model versions and dates **[FILL IN]**.
- **Compile repair:** compile failures were repaired in the same chat (up to 2 times, 3 screens used 1). Reported as a separate metric (first-try compile).
- **Instrument scope:**
  - ATF covers 3 checks;
  - contrast is estimated from screenshots;
  - Compose enlarges touch areas, so TT is measured statically and at runtime;
  - several WCAG aspects are blind spots (§4.2).
- **Decorative-icon policy:** stricter than Android guidance; results shown with and without it.
- **Beyond-WCAG category** (disabled field showing data) kept out of totals.
- **Repairer:**
  - one model, one pass;
  - prompt v5 frozen and developed on one screen (Music Player; results also reported without it);
  - v5 does not cover the v2.6 categories;
  - its example "Play button" likely induced vague descriptions;
  - Melodie's focus-loss hint likely induced the liveRegion type error.
- **Light mode only:** dark mode would mainly measure the pre-processor's theme injection, because the prompt forbids custom themes (future work).
- **Pre-processor:** deterministic fixes change the code under test. They are logged, audited and tested, but they are an intervention.
- **Instrument evolved during the study** (§4.4). The final battery ran on a single version (v2.8; one re-analysis on v2.9 to fix a double count).
- **Single device / Android version.**

## 8. Suggested paper outline (extended abstract)
1. **Introduction:** LLMs generate mobile UI; is it accessible, and can an LLM fix it?
2. **Melodie:** pipeline, analysers, repair loop.
3. **Study:** 10 screens × 3 LLMs, neutral prompts, calibrated instrument.
4. **Results:**
   - 27/30 screens with defects; runtime checks find almost none;
   - repair −73%, 16/26 clean;
   - side effects (6 new defects, 1 broken build).
5. **Discussion:**
   - semantic accessibility is invisible to runtime checks;
   - the repairer fixes symptoms without context;
   - strict policies can push repairs toward redundancy.
6. **Limitations and future work.**
